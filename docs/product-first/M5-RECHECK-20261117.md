## M5-RECHECK-001 — HIGH: stale plan response re-arms approval after user edits

Source: `web/director.js`, input/change listeners and the async form-submit handler. The user starts planning script A; while POST `/api/director/plan` is in flight, edits the form to B. `invalidate()` clears the plan, but the eventual response for A unconditionally sets `approvedPlan=plan` and `runButton.disabled=false`. Clicking run can therefore execute stale A while the form shows B. This contradicts M5 plan's stale-input fail-closed/user-approved plan contract.

**Repair:** save a normalized input fingerprint / monotonically increasing request generation on submit; invalidate it on every edit; only install a returned plan when its request generation and input still match; abort obsolete requests when possible; disable form edits during *run* or explicitly label a frozen approved revision. **Regression:** delay the plan API in a real Puppeteer browser, edit title and script during the request, resolve A, assert no runnable old graph and no `/run` call; re-plan B and verify a fresh approval works. Also test rapid successive requests and network errors.

## M5-RECHECK-002 — HIGH: completed render can duplicate a project after crash / missing receipt

Source: `src/director.ts` `DirectorService.run()`: the sole durable idempotency record (`director-m5/<planSha>.json`) is written only *after* `executeDirectorPlan` creates the project, performs voice, publishes a successful Studio job/artifact and returns. If the server/process stops or receipt write/rename fails in between, restarting and repeating the same approved plan finds no receipt and calls `Studio.create` again. The existing repeated-POST test only covers the *already persisted receipt* case. This violates the stated retry-after-ambiguous-result and durable recovery guarantee.

**Repair:** use a durable plan-keyed state journal/transaction before project creation, record project/revision/job/artifact IDs at every boundary, reconcile from Studio store on restart, resume or return a verified artifact without creating a second project. Atomic temp+rename with original expected revision and SHA checks; no optimistic PASS on incomplete journal. **Regression:** inject failure immediately after project creation, immediately after rendered artifact publication, and during receipt rename; reopen same data root, retry identical approved plan, assert exactly one project and no duplicate media job, with correct recovery receipt. Also test corrupt/stale journals and concurrent repeated requests.

## M5-RECHECK-003 — MEDIUM: voiced output can change approved timing/graph input without renewed review

Source: `src/audio.ts` `bindAudio()` sets `durationFrames=max(existing,ceil(audio.duration*24)+6)`; `src/director.ts` runs `Studio.voice` after approval, then renders its revised spec without checking whether scene timing changed or obtaining reapproval. The `render` graph node's `inputSha256` binds the *pre-voice* spec + voice flag, rather than the exact audio-bound render revision. In the two supplied sample films, duration happened to stay 432 frames, so the defect was not exercised.

**Repair:** distinguish planning/voice-preparation and final render approval, or enforce no timeline changes beyond an explicitly pre-approved bounded range. Bind final `revisionDigest`, all audio asset SHAs and timing to a validated graph execution receipt; make changed duration clearly visible in UI before final consent. **Regression:** long synthetic voice exceeding a 4-second planned scene, check that final timeline/hash cannot silently diverge from the approved graph; test ordinary unchanged timing and voice-disabled path.
